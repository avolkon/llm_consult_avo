**Контекст:**

- Обновить тексты бота (`/start`, ошибки авторизации) с понятной инструкцией для пользователя.
- Обновить документацию и зафиксировать новый UX-сценарий в архитектурных документах.

**Критерии готовности:**
- Пользователь из MAX может войти без понимания JWT/Swagger.
- После входа бот подтверждает авторизацию и принимает вопросы без команды `/token`.
- Текущий flow с `/token` сохранен как fallback на период миграции.

## [P3] Длинный ответ LLM: следующие части по подтверждению пользователя

**Статус:** backlog

**Плейсмент:**
- `project/services/bot_service/app/tasks/llm_tasks.py` (при необходимости — сохранение полного текста до нарезки)
- `project/services/bot_service/app/bot/handlers.py` (команда/триггер «продолжить», диспетчеризация)
- `project/services/bot_service/app/core/constants.py` (ключи Redis, TTL, префиксы)
- `project/services/bot_service/README.md`, `README.md`

**Контекст:**
Лимит MAX на одно исходящее сообщение (~3999 символов) и страховка `clip_text_for_max_api` обрезают текст; второй проход сжатия через LLM тратит лишние токены только при переливе. Пользователю иногда нужен **полный** длинный ответ. Запись в **буфер обмена** с сервера бота недоступна — зато можно хранить остаток на бэкенде и отдавать **чанками** после явного согласия (чтобы не спамить чат).

**Что нужно сделать:**
- После генерации ответа, если текст длиннее одного сообщения MAX: положить **полный** (или оставшийся после первой части) текст в Redis с привязкой к `max_user_id` / `sub`, с **TTL** и лимитом размера.
- В первое сообщение уложить первый чанк + короткая подсказка: как запросить продолжение (например, «напишите **ещё**» / **продолжить**).
- По входящему тексту-команде — отдать следующий чанк, обновить состояние; при исчерпании — сообщение об окончании.
- Учесть идемпотентность и конкурентность с существующим dedup входящих сообщений.
- Не включать в v1: автоматическая отправка всех частей подряд без подтверждения.

**Критерии готовности:**
- Пользователь при длинном ответе видит первую часть и может **по своей инициативе** получить следующие N частей в том же чате.
- Данные продолжения истекают по TTL и не копятся без ограничений.
- Текущий режим (одно сообщение + обрезка/сжатие) остаётся рабочим до реализации этой задачи.

## Перевести production DATABASE_URL на PostgreSQL

**Статус:** backlog

**Плейсмент:**
- `project/services/auth_service/.env`
- `project/.env.auth.example`
- `project/docker-compose.yml`
- `project/services/auth_service/README.md`
- `Разработка/Arch.txt`
- `ТЗ_МАКС.txt`

**Контекст:**
`DATABASE_URL` уже заполнен для локального режима. Для локальной разработки обычно достаточно SQLite:

```env
DATABASE_URL=sqlite+aiosqlite:///./auth.db
```

Для production лучше использовать PostgreSQL:

```env
DATABASE_URL=postgresql+asyncpg://user:password@postgres:5432/auth_db
```

**Что нужно сделать:**
- Добавить production-профиль БД на PostgreSQL.
- Добавить сервис PostgreSQL в `docker-compose.yml` или отдельный production compose-файл.
- Обновить env-шаблоны и документацию.
- Зафиксировать правила хранения production-секретов вне git.

## [P2] Production readiness: миграции, dead-letter и мониторинг outbox

**Статус:** backlog

**Плейсмент:**
- `project/services/auth_service/`
- `project/services/bot_service/app/bot/outbox_consumer.py`
- `project/services/bot_service/app/tasks/llm_tasks.py`
- `project/services/bot_service/app/core/config.py`
- `project/docker-compose.yml`
- `README.md`
- `Разработка/Arch.txt`

**Контекст:**
Текущая реализация достаточна для учебного v1: SQLite создаётся автоматически в local/dev/test, `max:outbox` обрабатывается через Redis LIST, ошибки доставки логируются и ограниченно ретраятся. Для production нужны управляемые миграции БД, отдельный dead-letter/retry контур и наблюдаемость очереди, иначе эксплуатационные сбои будет сложно диагностировать и безопасно восстанавливать.

**Что нужно сделать:**
- Добавить полноценную схему миграций БД для production PostgreSQL (например Alembic или эквивалентный механизм).
- Описать порядок применения миграций при деплое.
- Добавить dead-letter/retry queue для сообщений, которые не удалось доставить в MAX после лимита попыток.
- Добавить мониторинг размера `max:outbox` и alert threshold для роста очереди.
- Добавить метрики/логи по успешным доставкам, ошибкам доставки, retry и dead-letter.
- Обновить README и архитектурную документацию с production-ограничениями.

**Критерии готовности:**
- Production-БД разворачивается через миграции, а не ручное создание таблиц.
- Сообщения после исчерпания retry не теряются молча, а попадают в dead-letter контур.
- Есть проверяемый способ увидеть размер `max:outbox` и число failed/retried сообщений.
- Документация описывает порядок восстановления после сбоя доставки.
