================================================================================
     КРИТИЧНЫЕ / ВЫСОКИЕ — инфраструктура и границы доверия
================================================================================

1. Redis и RabbitMQ как внутренняя граница
   - Celery принимает JSON-задачи (sub, role, prompt). Доступ к брокеру без
     изоляции → произвольные задачи от имени чужого sub, расход квот LLM.
   - Очередь max:outbox в Redis: consumer доверяет JSON. Запись в Redis при
     скомпрометированном или открытом инстансе → подделка доставки в MAX,
     спам, DoS очереди.
   - Ключи max_auth:*, user_chat:*: компрометация Redis → подмена сессий.

   Рекомендации: недоступность брокера и Redis из интернета; сильные пароли;
   ACL/TLS; отдельная сеть; не использовать guest в production.

2. Webhook MAX (maxapi / FastAPIMaxWebhook)
   - В репозитории не видно явной собственной проверки подписи/секрета входящего
     webhook — полагаться на поведение maxapi и требования платформы MAX.
   - Риск: подделка событий, если эндпоинт открыт и проверка не гарантирована.

   Рекомендации: сверить документацию MAX/maxapi; при необходимости —
     секрет в URL, подпись тела, allowlist IP, WAF.

3. JWT в чате мессенджера
   - Команда /token передаёт сырой JWT через MAX. Канал считать недоверенным
     для долгоживущих секретов (логи, история, скриншоты).

================================================================================
                          СРЕДНИЙ УРОВЕНЬ
================================================================================

4. Лимит размера тела только по Content-Length
   - Middleware проверяет заголовок Content-Length. Обход возможен при
     отсутствии/ложном заголовке или chunked (зависит от прокси и ASGI).
   - Рекомендации: жёсткий лимит на reverse proxy; при необходимости —
     ограничение при чтении тела.

5. Нет rate limit на POST /auth/register
   - На /auth/login есть slowapi; регистрация без лимита → массовая регистрация,
     нагрузка на БД, перечисление занятых email (см. п.7).

6. Слабая политика паролей
   - RegisterRequest: min_length=6 — недостаточно для публичного сервиса.
   - Рекомендации: длина и сложность, блоклисты, при необходимости —
     проверка утёкших паролей.

7. Утечка признаков по email
   - Регистрация: 409 при занятом email. Логин: единое 401 — хорошо.
   - Регистрация всё же раскрывает факт существования учётной записи.

8. Логирование фрагментов промптов (handlers.py)
   - INFO с sub, max_user_id и префиксом промпта — ПДн/чувствительные данные
     в централизованных логах. Рекомендации: минимизация, маскирование, срок
     хранения, доступ по ролям.

9. OPENROUTER_BASE_URL из окружения
   - При компрометации env трафик можно направить на злоумышленный хост.
   - Рекомендации: контроль секретов; в prod — доверенный хост (pin/allowlist).

10. JWT decode: verify_aud=False
    - Допустимо при одной аудитории; при появлении нескольких клиентов —
      риск переиспользования токена без явного aud.

11. jwt_alg из env без жёсткого allowlist
    - Рекомендация: разрешить только ожидаемые алгоритмы (например HS256)
      через валидацию конфигурации.

================================================================================
                    НИЖЕ СРЕДНЕГО / глубина защиты
================================================================================

12. Prompt injection и regex-фильтр
    - is_prompt_suspicious снижает только типовые формулировки; обходы через
     перефраз, языки, кодировки. Основной риск остаётся на стороне LLM и политики.

13. OutboxItem: нет верхней границы длины поля text
    - Риск DoS по Redis и при отправке в MAX.

14. Bot FastAPI: нет набора security headers как у auth_service
    - Выравнивание заголовков — простое улучшение единообразия.

15. Rate limit: get_remote_address
    - За reverse proxy без корректной настройки X-Forwarded-For лимит может
     применяться неверно. Нужны trusted proxies.

16. Swagger /docs в production
    - Разведка API. Рекомендация: отключить или закрыть (VPN, basic auth).

17. Docker Compose (dev): порты Redis, RabbitMQ, management UI
    - На общедоступном хосте увеличивает поверхность атаки.

================================================================================
                    ПОЛОЖИТЕЛЬНЫЕ НАБЛЮДЕНИЯ (кратко)
================================================================================

- Пароли: bcrypt/passlib; JWT с exp; sub в токене согласован с login/register.
- Запросы к БД через ORM, явного SQL injection в репозитории не выявлено.
- jwt_secret: обязательность и отторжение плейсхолдеров (auth и bot).
- Ограничение длины промпта, обобщённые ответы пользователю при ошибках LLM.
- Атомарность register_token через Redis WATCH/MULTI (снижение гонок).
