================================================================================
  Доверие к входящему webhook MAX (модель угроз и меры)
================================================================================

Контекст
  Bot_service поднимает HTTP-эндпоинт webhook (maxapi.FastAPIMaxWebhook). Вопрос
  ИБ: кто может слать события на этот URL и как отсекается подделка.

Что делает библиотека maxapi
  Клиент Bot создаётся с MAX_BOT_TOKEN. Платформа MAX при доставке обновлений
  на зарегистрированный URL, как правило, использует тот же токен/механизм
  аутентификации API бота для проверки легитимности запроса. Конкретная схема
  (заголовки, подпись тела, секрет в path) задаётся документацией MAX и версией
  maxapi — при обновлении зависимости перепроверяйте исходники обработчика
  FastAPIMaxWebhook.

Компенсирующие меры (рекомендуется комбинировать по политике заказчика)

  1. Сеть: webhook слушает только во внутренней сети; наружу — reverse proxy
     (nginx/traefik) с TLS и ограничением client_max_body_size.
  2. Секрет в пути: задайте WEBHOOK_PATH с длинным неугадываемым сегментом
     (например /hooks/<random>) и зарегистрируйте только этот URL в кабинете MAX.
  3. IP allowlist: если у MAX есть стабильные исходящие IP — ограничьте доступ
     на уровне firewall / cloud security group.
  4. WAF / rate limit на уровне прокси против массовых POST на webhook.

  Итог
  Подлинность запросов опирается на MAX + maxapi + вашу сетевую изоляцию.
  Документируйте выбранную комбинацию мер в эксплуатационной инструкции.

--------------------------------------------------------------------------------
  Реализация в bot_service (дополнительно к мерам выше)
--------------------------------------------------------------------------------

  Переменные окружения:
    WEBHOOK_REQUEST_SECRET   — если задан, для POST на WEBHOOK_PATH нужен заголовок
                               WEBHOOK_REQUEST_HEADER (по умолчанию x-webhook-secret)
                               с тем же значением. Платформа MAX этот заголовок не
                               присылает: типичная схема — закрытый URL до reverse proxy,
                               proxy добавляет заголовок и проксирует на приложение.

    WEBHOOK_REQUEST_HEADER   — имя заголовка (регистр может отличаться).

    WEBHOOK_ALLOWED_CIDRS    — через запятую сети, например 203.0.113.0/24,2001:db8::/32;
                               если задано, POST на webhook принимаются только с этих IP.

    WEBHOOK_FORWARDED_FOR_TRUST_HOPS
                             — если 1 и выше, для проверки CIDR берётся первая часть
                               X-Forwarded-For; включайте только если прокси под вашим
                               контролем и подделка XFF с недоверенной стороны исключена.

  Пример фрагмента nginx (идея, не копировать без адаптации под ваш TLS и upstream):
    location /hooks/секретный_сегмент/ {
      proxy_set_header X-Webhook-Secret $webhook_hmac_secret;  # из env nginx
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_pass http://bot_upstream;
    }

  Целостность Redis (см. README, REDIS_INTEGRITY_SECRET):
    Общий HMAC для записей max_auth:* и для строк max:outbox снижает риск подмены
    при компрометации только Redis без утечки секрета целостности; не заменяет
    сильный REDIS_URL, сетевой периметр и пароль брокера.
