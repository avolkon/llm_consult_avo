# Правила разработки для ИИ-агента (DevRules)

Документ фиксирует договорённости по работе ассистента в репозитории **llm_consult_avo**. Деталь машинно-читаемых правил Cursor — в `.cursor/rules/*.mdc`; здесь — человекочитаимое резюме и полный охват процесса.

---

## 1. Git и коммиты

- Перед `git commit`: ассистент **предлагает текст сообщения**, **показывает его пользователю**, **ждёт явного согласования**, затем выполняет коммит (см. `.cursor/rules/git-commit-workflow.mdc`).
- Не коммитить локальные секреты, `*.env` с реальными токенами, локальные SQLite (`auth_service/*.db` игнорируются в `.gitignore`).
- Предпочтительно: **заголовок коммита на английском**, текст тела (если есть) **на русском** — полные предложения, без телеграфного стиля.

---

## 2. Секреты и переменные окружения

- **Не читать и не выводить в чат** содержимое файлов:
  - `project/services/bot_service/.env`
  - `project/services/auth_service/.env`
  - иных `.env`, где могут быть боевые секреты.
- Разрешено: `.env.example`, проверка факта «ключ задан / пустой» **без печати значений**; статусы вида `MAX_BOT_TOKEN=set`.
- Режим **`env-`**: временно разрешить работу **только** с `.env`, открытым в активном редакторе, после предупреждения и подтверждения пользователем **`u`**. Не печатать реальные токены; маскировать при необходимости.
- Снятие режима **`env-`**: по **`env+`** или при **отсутствии активности более 3 минут** — снова не читать `.env` без нового протокола.

Подробности: `.cursor/rules/secret-env-no-read.mdc`.

---

## 3. Код и объём изменений

- Менять **только то, что нужно для задачи**: без побочных рефакторингов и лишних файлов.
- **Не добавлять** по своей инициативе markdown-документацию, кроме случаев, когда пользователь явно просит (этот файл создан по запросу).
- Перед правками **читать контекст**; соблюдать стиль проекта (имена, типы, импорты, уровень комментариев).
- **Переиспользовать** существующие абстракции; избегать лишних `try/except`, «защитного» кода и комментариев к очевидному.
- Не удалять чужие релевантные комментарии без необходимости.
- Каждая строка диффа должна относиться к запросу.

---

## 4. Среда выполнения

- Считать окружение **реальным**: есть shell и сеть; **выполнять** команды самому, а не ограничиваться инструкциями «запустите у себя».
- При сбоях — пробовать альтернативы и диагностику, не сдаваться после одной ошибки.
- Поле **Today's date** в контексте сессии считать авторитетным для текущей даты/года.

---

## 5. Общение и цитирование кода

- В ответах пользователю: связный тех. текст, **без** избыточного bold/бэктиков и символа **§**.
- Ссылаться на существующий код блоками цитирования в формате Cursor:

  ```start:end:path/to/file
  ```

  Открывающие **```** — на отдельной строке.
- Учитывать **историю диалога** и неявную цель, не только последнюю реплику.

---

## 6. Тесты и качество

- После значимых изменений в Python-сервисах по возможности запускать **pytest** и **ruff** в соответствующем сервисе.
- Сохранять проходящие тесты; при добавлении функциональности — осмысленные тесты в стиле проекта.

---

## 7. Архитектура проекта (напоминание)

- **auth_service**: регистрация, логин, JWT; не знает про MAX/Redis/Celery деталей бота.
- **bot_service**: MAX (maxapi), JWT-проверка, Redis (`max_auth` / `user_chat`, `max:outbox`), Celery → OpenRouter.
- Источник требований по смыслу: `ТЗ_МАКС.txt`, `README.md`, `Arch.txt` при наличии.

---

## 8. Обновление этого файла

- При появлении новых договорённостей с пользователем разделы дополняются или меняются по явной просьбе.
- Дублирование с `.mdc`: в `.mdc` — то, что Cursor должен применять автоматически; здесь — объяснение и контекст для людей.
