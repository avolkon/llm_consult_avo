Эпик 3. Celery + OpenRouter + Outbox Producer

Статус: Планирование
Приоритет: Высокий
Цель: Реализовать асинхронную обработку LLM-запросов через Celery и
публикацию результатов в Redis outbox (`max:outbox`).

Согласованное отклонение от базового ТЗ:
- task-контракт фиксируется как `llm_request(sub, role, prompt)`;
- Celery worker не отправляет в MAX напрямую, а публикует в `max:outbox`.

Границы ответственности:
1) Делает:
- получает задачи `llm_request(sub, role, prompt)` из RabbitMQ;
- вызывает OpenRouter и получает текст ответа;
- определяет маршрут доставки через `user_chat:{sub}`;
- публикует результат в `max:outbox` через `RPUSH`.

2) Не делает:
- не импортирует `maxapi`;
- не вызывает MAX API;
- не занимается приемом сообщений от пользователя.

Бизнес-результат эпика:
- входящий пользовательский запрос обрабатывается асинхронно;
- бот не блокируется на ожидании LLM;
- ответ готовится к доставке через outbox-механизм.

Функциональный объем (MVP):
1) `celery_app` с broker RabbitMQ;
2) OpenRouter client;
3) task `llm_request`;
4) `OutboxItem` модель;
5) тесты OpenRouter client и task.

Обязательные требования к качеству:
- синхронный клиент OpenRouter в Celery worker (v1);
- обработка сетевых и API ошибок OpenRouter;
- `task_id` берется из Celery request;
- отсутствие хардкода ключей Redis;
- логирование без утечки секретов.

Артефакты по итогам эпика:
- `infra/celery_app.py`;
- `services/openrouter_client.py`;
- `tasks/llm_tasks.py`;
- `models/outbox.py`;
- тесты по task/client контракту.

Definition of Done:
1) Worker принимает задачи из очереди и не падает на штатных ошибках LLM.
2) Успешный результат попадает в `max:outbox`.
3) При отсутствии `user_chat:{sub}` задача завершается корректно с логом.
4) Контракт outbox согласован с Response Sender (Эпик 4).
5) Тесты сценариев Эпика 3 проходят стабильно.
