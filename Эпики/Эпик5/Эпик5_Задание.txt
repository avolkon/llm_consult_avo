# 🎯 Задание на разработку: EPIC5-STAGE1 Тестовая инфраструктура

## Контекст
Этап 1 создает единый тестовый каркас для двух сервисов и снижает риск
нестабильных/неповторяемых проверок.

## Текущее состояние
**Файл:** `project/services/auth_service/pytest.ini`, `project/services/bot_service/pytest.ini`, `*/tests/conftest.py`  
**Функция/класс:** тестовый bootstrap и фикстуры  
**Текущий вывод/поведение:** тестовая инфраструктура может быть несогласованной  
**Необходимый вывод/поведение:** единые правила запуска async тестов и фикстур

## Требования ТЗ
Тесты должны быть разделены на модульные/интеграционные, без зависимости от реальных внешних сервисов.

## Задача
Сформировать стабильную и воспроизводимую инфраструктуру тестирования.

## Технические требования
### 1. Изменения в тестовом bootstrap
**Логика работы:**
1. Настроить `pytest.ini` для каждого сервиса.
2. Подготовить общие фикстуры для тестовой БД/Redis/mock сервисов.
3. Зафиксировать соглашение по маркировке тестов.

### 2. Формат вывода
```
pytest run -> stable, deterministic, no external network required
```

### 3. Обработка ошибок
```python
# flaky async tests
Использовать корректные asyncio fixtures и изолированное состояние.
```

## Файлы для изменения
- `project/services/auth_service/pytest.ini`
- `project/services/bot_service/pytest.ini`
- `project/services/auth_service/tests/conftest.py`
- `project/services/bot_service/tests/conftest.py`
- **Не изменять:** business logic без необходимости.

## Пример реализации
```python
На этом этапе код не приводится. Реализация выполняется в отдельной итерации.
```

## Тестирование

## Критерии приемки
- [ ] Тесты запускаются единообразно в обоих сервисах.
- [ ] Async тесты стабильны.
- [ ] Нет обязательной внешней сети/сервисов для базового прогона.

## Примечания для разработчика
1. Избегать глобального состояния между тестами.
2. Делать фикстуры минимально достаточными.
