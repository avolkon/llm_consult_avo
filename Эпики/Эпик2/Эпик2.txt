Эпик 2. Bot Service Core — MAX интеграция и Redis маппинг

Статус: Планирование
Приоритет: Высокий
Цель: Реализовать базовый контур Bot Service, который принимает JWT в чате MAX,
проверяет авторизацию через Redis-маппинг и отправляет LLM-запросы в Celery.

Границы ответственности:
1) Делает:
- принимает сообщения MAX через maxapi (polling/webhook);
- валидирует JWT (без выпуска токена);
- поддерживает Redis-состояние `max_auth:*` и `user_chat:*` с TTL по `exp`;
- вызывает Celery задачу `llm_request.delay(sub, role, prompt)`.

2) Не делает:
- не управляет пользователями и паролями;
- не вызывает Auth Service напрямую;
- не вызывает OpenRouter напрямую из handlers;
- не отправляет LLM-ответы в MAX из Celery worker.

Бизнес-результат эпика:
- пользователь может отправить `/token <JWT>`;
- бот сохраняет авторизацию в Redis;
- бот принимает текстовые сообщения только при валидной авторизации;
- бот асинхронно передает запрос в очередь Celery.

Функциональный объем (MVP):
1) `/token <jwt>` в чате MAX;
2) проверка доступа по Redis;
3) отправка задачи в Celery;
4) технический `/health` для webhook режима;
5) базовые тесты JWT, маппинга и handlers.

Обязательные требования к качеству:
- единый конфиг через `.env` и `pydantic-settings`;
- отсутствие хардкода Redis-ключей;
- отсутствие MAX API вызовов в Celery worker;
- читаемая обработка ошибок авторизации и Redis;
- тесты не должны зависеть от реального Redis/RabbitMQ/MAX.

Артефакты по итогам эпика:
- `bot_service` core-модули (`core/config.py`, `core/jwt.py`, `infra/redis.py`,
  `services/auth_mapping.py`, `bot/handlers.py`);
- обновленные entrypoint для polling/webhook;
- документированные env-параметры;
- тесты core-логики.

Definition of Done:
1) `/token <jwt>` сохраняет валидный маппинг в Redis.
2) Сообщение без авторизации получает отказ.
3) Сообщение с авторизацией вызывает `llm_request.delay(...)`.
4) Тесты по Эпику 2 проходят стабильно.
5) Контракт с Эпиком 3 зафиксирован (`sub`, `role`, `prompt`).
