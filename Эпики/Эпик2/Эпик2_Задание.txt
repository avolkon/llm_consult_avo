# 🎯 Задание на разработку: EPIC2-STAGE1 Настройка Bot Service и maxapi

## Контекст
Этап 1 запускает технический контур Bot Service и задает единый способ работы в
режимах polling/webhook. Это база для JWT и Redis-логики в следующих этапах.

## Текущее состояние
**Файл:** `project/services/bot_service/app/main.py`, `project/services/bot_service/app/poll.py`, `project/services/bot_service/app/core/config.py`  
**Функция/класс:** сборка FastAPI + maxapi dispatcher + Settings  
**Текущий вывод/поведение:** режимы запуска и конфигурация могут быть неполными/несинхронными  
**Необходимый вывод/поведение:** сервис стабильно запускается в polling/webhook, имеет `/health`, читает `.env`

## Требования ТЗ
Bot Service работает как MAX-бот, поддерживает polling/webhook, имеет health endpoint и использует конфигурацию из окружения.
Согласованное терминологическое правило для этапов EPIC2: в Redis хранится auth-состояние
`max_auth`/`user_chat`, а не JWT по ключу `token:<id>`.

## Задача
Зафиксировать и реализовать технический каркас Bot Service для работы с MAX в двух режимах.

## Технические требования

### 1. Изменения в каркасе и конфигурации
**Логика работы:**
1. Уточнить settings (`MAX_BOT_TOKEN`, `JWT_SECRET`, `REDIS_URL`, `CELERY_BROKER_URL`, delivery mode).
2. Зафиксировать `create_app()` и `/health` для webhook режима.
3. Зафиксировать отдельный entrypoint polling через `Dispatcher.start_polling(bot)`.

### 2. Формат вывода
```
GET /health -> 200
{
  "status": "ok",
  "transport": "max"
}
```

**Где:**
- `status` - индикатор доступности.
- `transport` - тип транспорта бота.

### 3. Обработка ошибок
```python
# Ошибка токена бота/инициализации MAX
Логировать и завершать запуск без перехода в рабочий цикл.

# Ошибка конфигурации окружения
Поднимать валидационную ошибку settings до старта приложения.
```

## Файлы для изменения
- `project/services/bot_service/app/main.py` - webhook приложение и /health.
- `project/services/bot_service/app/poll.py` - polling entrypoint.
- `project/services/bot_service/app/core/config.py` - обязательные env settings.
- `project/services/bot_service/.env.example` - шаблон переменных.
- **Не изменять:** `project/services/auth_service/*`.

# 🎯 Задание на разработку: EPIC2-STAGE2 JWT валидация в Bot Service

## Контекст
Этап 2 вводит единый контракт проверки JWT в Bot Service без зависимости от Auth Service runtime.

## Текущее состояние
**Файл:** `project/services/bot_service/app/core/jwt.py`  
**Функция/класс:** `decode_and_validate(token)`  
**Текущий вывод/поведение:** проверка токена может быть неполной/несогласованной  
**Необходимый вывод/поведение:** валидный JWT возвращает payload, невалидный — доменную ошибку

## Требования ТЗ
Bot Service должен валидировать подпись и `exp`, извлекать `sub` и `role`, но не выпускать JWT.

## Задача
Реализовать и зафиксировать контракт `decode_and_validate` для handlers.

## Технические требования

### 1. Изменения в JWT сервисе
**Логика работы:**
1. Проверять подпись токена по `JWT_SECRET` и `JWT_ALG`.
2. Проверять срок действия `exp`.
3. Возвращать payload словарем при успехе, `ValueError` при ошибке.

### 2. Формат вывода
```
decode_and_validate(token) -> {
  "sub": "<user_id>",
  "role": "<user|admin>",
  "iat": <timestamp>,
  "exp": <timestamp>
}
```

**Где:**
- `sub` - идентификатор пользователя Auth Service.
- `role` - роль для бизнес-ограничений.

### 3. Обработка ошибок
```python
# Невалидная подпись/структура
Поднимать ValueError с безопасным текстом.

# Истекший токен
Поднимать ValueError с явным указанием на истечение срока действия.
```

## Файлы для изменения
- `project/services/bot_service/app/core/jwt.py` - контракт валидации.
- `project/services/bot_service/tests/test_core/test_jwt.py` - тесты JWT.
- **Не изменять:** модули Auth Service.

## Пример реализации
```python
На этом этапе код не приводится. Реализация выполняется в отдельной итерации.
```

## Тестирование
не пишешь на этапе разработки

## Критерии приемки
- [ ] Валидный JWT корректно декодируется.
- [ ] Невалидный JWT отклоняется.
- [ ] Истекший JWT отклоняется.

## Примечания для разработчика
1. Не логировать токен целиком.
2. Не добавлять сетевые вызовы в JWT-модуль.
3. Сохранять минимальный и стабильный интерфейс функции.

## Время на выполнение
Оценка: 1-2 часов (включая тестирование)

# 🎯 Задание на разработку: EPIC2-STAGE3 Redis маппинг авторизации

## Контекст
Этап 3 вводит двунаправленное состояние авторизации в Redis, чтобы связать MAX чат и Auth `sub`.

## Текущее состояние
**Файл:** `project/services/bot_service/app/infra/redis.py`, `project/services/bot_service/app/services/auth_mapping.py`, `project/services/bot_service/app/core/constants.py`  
**Функция/класс:** Redis client, ключи, register/get helpers  
**Текущий вывод/поведение:** маппинг может быть неполным или без полной инвалидации  
**Необходимый вывод/поведение:** корректный двунаправленный маппинг с TTL и инвалидацией

## Требования ТЗ
Состояние авторизации хранится в Redis и привязано к сроку JWT; bot проверяет токен по состоянию в Redis.

## Задача
Реализовать устойчивый Redis маппинг `max_auth`/`user_chat` с инвалидацией устаревших связей.

## Технические требования

### 1. Изменения в Redis слоях
**Логика работы:**
1. Зафиксировать ключи: `max_auth:{max_user_id}` и `user_chat:{sub}`.
2. Реализовать `register_token(...)` с удалением старых связей в обе стороны.
3. Реализовать `get_auth(max_user_id)` и `get_chat(sub)` helpers.

### 2. Формат вывода
```
max_auth:{max_user_id} = {"sub":"<sub>","role":"<role>"} (TTL = exp)

```

**Где:**

### 3. Обработка ошибок

# 🎯 Задание на разработку: EPIC2-STAGE4 Handlers `/token` и текстовых сообщений

## Контекст
Этап 4 связывает JWT + Redis + Celery в пользовательский сценарий чата MAX.

## Текущее состояние
**Файл:** `project/services/bot_service/app/bot/handlers.py`, `project/services/bot_service/app/bot/dispatcher.py`  
**Функция/класс:** обработчики команд и сообщений  
**Текущий вывод/поведение:** handlers могут быть заглушками  
**Необходимый вывод/поведение:** корректный `/token` поток и отправка `llm_request.delay`

## Требования ТЗ
Бот должен принимать `/token <JWT>`, сохранять авторизацию и отклонять сообщения без валидного состояния.

## Задача
Реализовать handlers для команды `/token` и обычного текста с интеграцией в Redis и Celery.

## Технические требования

### 1. Изменения в handlers
**Логика работы:**
1. `/token <jwt>`: decode -> register_token -> ответ пользователю.
2. Текст: get_auth -> если нет, ответ об отсутствии авторизации.
3. Текст при авторизации: `llm_request.delay(sub, role, prompt)` -> ответ "запрос принят".

### 2. Формат вывода
```
/token success -> "Токен принят. Можно отправлять текст для LLM."
no auth -> "Сначала авторизуйтесь: /token <JWT от auth_service>"
accepted -> "Запрос отправлен, ответ появится в этом чате."
```

**Где:**
- сообщения пользователю формируются в handlers.

### 3. Обработка ошибок
```python
# Невалидный JWT
Отвечать пользователю с пояснением о недействительном токене.

# Ошибка Redis/Celery
Логировать и отправлять безопасное сообщение о временной недоступности.
```

## Файлы для изменения
- `project/services/bot_service/app/bot/handlers.py` - логика `/token` и текста.
- `project/services/bot_service/app/bot/dispatcher.py` - регистрация handlers.
- `project/services/bot_service/app/tasks/llm_tasks.py` - проверить сигнатуру задачи.
- **Не изменять:** OpenRouter детали и outbox consumer (Эпик 3/4).
