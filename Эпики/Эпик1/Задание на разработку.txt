ЗАДАНИЕ НА РАЗРАБОТКУ
Эпик 1: Auth Service
Формат выполнения: поэтапно, 6 итераций
Ограничение текущей итерации: код не писать, только подготовка заданий и критериев

-----------------------------------
ЭТАП 1. Каркас приложения и конфигурация
-----------------------------------
Цель этапа:
Собрать базовый FastAPI-каркас auth_service и централизованную конфигурацию через pydantic-settings.

Задания:
1) Уточнить структуру модулей (main/core/api/db/repositories/usecases/schemas/tests).
2) Сформировать перечень обязательных переменных окружения:
   - APP_NAME
   - ENV
   - JWT_SECRET
   - JWT_ALG
   - ACCESS_TOKEN_EXPIRE_MINUTES
   - DATABASE_URL (или SQLITE_PATH)
3) Определить правила дефолтных значений для local/dev окружения.
4) Зафиксировать endpoint /health и базовую сборку роутеров.
5) Зафиксировать использование lifespan (без deprecated on_event).

Критерии приемки этапа:
- сервис запускается;
- /health отвечает 200;
- конфигурация читается из .env;
- отсутствует бизнес-логика в main.py.

Риски:
- неявные/несогласованные env-переменные между средами;
- дублирование конфигурации в нескольких модулях.

-----------------------------------
ЭТАП 2. Модель данных и доступ к БД
-----------------------------------
Цель этапа:
Спроектировать и реализовать слой данных для пользователей.

Задания:
1) Определить ORM-модель User:
   - id
   - email (unique)
   - password_hash
   - role
   - created_at
2) Спроектировать асинхронную сессию БД (engine + sessionmaker).
3) Зафиксировать репозиторный контракт:
   - get_by_email
   - get_by_id
   - create
4) Определить правила транзакционности и обработки ошибок БД.
5) Зафиксировать, что репозиторий не зависит от FastAPI/HTTP.

Критерии приемки этапа:
- модель и ограничения БД согласованы;
- репозиторные операции покрывают потребности usecase;
- слой данных отделен от API слоя.

Риски:
- отсутствие уникальности email на уровне БД;
- смешивание бизнес-логики и SQL в одном слое.

-----------------------------------
ЭТАП 3. Безопасность и JWT
-----------------------------------
Цель этапа:
Определить стандарт безопасности паролей и токенов.

Задания:
1) Зафиксировать алгоритм хеширования пароля (passlib/bcrypt).
2) Уточнить контракт create_access_token:
   - обязательные claims: sub, role, iat, exp.
3) Уточнить контракт decode_token:
   - проверка подписи;
   - проверка срока действия;
   - единый формат ошибок.
4) Определить каталог доменных исключений:
   - UserAlreadyExistsError
   - InvalidCredentialsError
   - InvalidTokenError
   - TokenExpiredError
   - UserNotFoundError
   - PermissionDeniedError
5) Зафиксировать требования к журналированию (без утечки секретов).

Критерии приемки этапа:
- спецификация JWT согласована с Bot Service;
- единые правила ошибок и безопасной обработки токенов;
- отсутствует хранение/логирование открытых паролей и JWT секретов.

Риски:
- несовместимость claims с потребителями;
- неоднозначная обработка истекшего токена.

-----------------------------------
ЭТАП 4. Бизнес-логика и API
-----------------------------------
Цель этапа:
Описать сценарии register/login/me как единый бизнес-поток.

Задания:
1) Согласовать входные/выходные схемы:
   - RegisterRequest
   - TokenResponse
   - UserPublic
2) Формализовать usecase:
   - register()
   - login()
   - me()
3) Уточнить API-роуты и статусы:
   - POST /auth/register
   - POST /auth/login
   - GET /auth/me
4) Определить dependency chain:
   - get_db()
   - get_current_user()
   - get_auth_uc()
5) Зафиксировать правило: роуты тонкие, бизнес-логика только в usecase.

Критерии приемки этапа:
- контракты API непротиворечивы;
- статусы ошибок согласованы;
- бизнес-логика отделена от транспорта.

Риски:
- дублирование валидации между роутами и usecase;
- привязка usecase к FastAPI-типам.

-----------------------------------
ЭТАП 5. Тестирование
-----------------------------------
Цель этапа:
Сформировать тестовую стратегию для функционала эпика.

Задания:
1) Спроектировать модульные тесты:
   - hash_password/verify_password
   - create_access_token/decode_token
2) Спроектировать интеграционные тесты API:
   - register -> login -> me
3) Спроектировать негативные тесты:
   - duplicate email -> 409
   - wrong password -> 401
   - missing/invalid token -> 401
4) Зафиксировать тестовые фикстуры:
   - test DB (in-memory SQLite для быстрых тестов)
   - dependency override для get_db
5) Зафиксировать минимальные метрики качества:
   - все тесты проходят
   - целевое покрытие >= 80%

Критерии приемки этапа:
- тестовый план покрывает позитивные и негативные сценарии;
- отсутствуют внешние сетевые зависимости в unit/integration тестах.

Риски:
- флаки тесты из-за неуправляемого состояния БД;
- тесты зависят от локальной среды разработчика.

-----------------------------------
ЭТАП 6. Финализация, документация, приемка
-----------------------------------
Цель этапа:
Подготовить эпик к закрытию и передаче в следующий контур.

Задания:
1) Сформировать чеклист code review:
   - нет секретов в коде;
   - Pydantic-схемы не содержат password_hash;
   - исключения доменные, не ручные HTTPException в бизнес-логике;
   - корректная асинхронность/await.
2) Подготовить инструкцию ручной валидации (curl/Swagger сценарии).
3) Обновить README auth_service:
   - переменные окружения;
   - команды запуска;
   - примеры запросов.
4) Зафиксировать критерии готовности к Эпику 2:
   - JWT совместим по claims;
   - стабильный контракт /auth/login и /auth/me.
5) Подготовить краткий отчет о выполнении (что сделано/что осталось).

Критерии приемки этапа:
- документация синхронизирована с фактом реализации;
- критерии DoD эпика закрыты;
- эпик можно передавать в реализацию следующего контура.

Риски:
- технический долг без фиксации ограничений;
- расхождение документации и фактического поведения API.

-----------------------------------
Формат работы в следующих итерациях
-----------------------------------
1) Берем один этап.
2) Делаем декомпозицию задач в подзадачи.
3) Реализуем и проверяем только текущий этап.
4) Фиксируем промежуточный результат и только затем идем дальше.
