# 🎯 Задание на разработку: EPIC4-STAGE1 Outbox Consumer loop

## Контекст
Этап 1 реализует ядро доставки: цикл чтения `max:outbox` и отправка в MAX.

## Текущее состояние
**Файл:** `project/services/bot_service/app/bot/outbox_consumer.py`  
**Функция/класс:** `outbox_consumer_loop(bot)`  
**Текущий вывод/поведение:** логика может быть неполной или без обработки edge-cases  
**Необходимый вывод/поведение:** стабильный consumer с `BLPOP`, timeout handling и отправкой в MAX

## Требования ТЗ
Результат LLM должен доставляться пользователю из очереди Redis, а не из Celery worker.

## Задача
Реализовать устойчивый consumer для обработки `max:outbox`.

## Технические требования
### 1. Изменения в consumer
**Логика работы:**
1. Выполнять `BLPOP max:outbox timeout=1.0`.
2. Обрабатывать `None` как штатный timeout.
3. Парсить элемент и вызывать `bot.send_message`.

### 2. Формат вывода
```
BLPOP -> OutboxItem(max_user_id, text, task_id, created_at) -> send_message
```

### 3. Обработка ошибок
```python
# Невалидный JSON outbox
Логировать и пропускать элемент.

# Ошибка send_message
Логировать с task_id/max_user_id и продолжать цикл.
```

## Файлы для изменения
- `project/services/bot_service/app/bot/outbox_consumer.py` - core loop.
- `project/services/bot_service/app/models/outbox.py` - schema parsing.
- **Не изменять:** Celery task и OpenRouter client.

# 🎯 Задание на разработку: EPIC4-STAGE3 Идемпотентность и дедупликация (опционально v1)

## Контекст
Этап 3 нужен для production-устойчивости при ретраях и повторных доставках.

## Текущее состояние
**Файл:** `project/services/bot_service/app/bot/outbox_consumer.py`  
**Функция/класс:** dedup layer вокруг `task_id`  
**Текущий вывод/поведение:** возможна повторная отправка одинакового task  
**Необходимый вывод/поведение:** повторные task_id не отправляются повторно

## Требования ТЗ
Идемпотентность должна быть предусмотрена для надежной доставки.

## Задача
Добавить dedup-проверку на `task_id` через Redis.

## Технические требования
### 1. Изменения в dedup логике
**Логика работы:**
1. Для элемента с `task_id` выполнять `SETNX processed:<task_id>`.
2. Если ключ уже есть, пропускать отправку.
3. Ставить `EXPIRE` на processed ключ.

### 2. Формат вывода
```
task_id new -> send
task_id exists -> skip
```

### 3. Обработка ошибок
```python
# Ошибка Redis на dedup check
Логировать и применять fail-open или fail-closed по конфигу (по умолчанию fail-open).
```

# 🎯 Задание на разработку: EPIC4-STAGE4 Error policy и retry delivery

## Контекст
Этап 4 вводит управляемую политику повторной доставки при ошибках MAX API.

## Текущее состояние
**Файл:** `project/services/bot_service/app/bot/outbox_consumer.py`  
**Функция/класс:** error handling policy  
**Текущий вывод/поведение:** ошибки могут только логироваться  
**Необходимый вывод/поведение:** политика retry/skip определена и управляется конфигом

## Требования ТЗ
При ошибках доставки система не должна терять сообщения "молча".

## Задача
Определить и реализовать стратегию обработки ошибок доставки.

## Технические требования
### 1. Изменения в error policy
**Логика работы:**
1. Классифицировать ошибки (временные/постоянные).
2. Для временных ошибок применять ограниченный retry.
3. Для исчерпанного retry логировать окончательный failure с контекстом.

### 2. Формат вывода
```
send fail -> retry_count + 1 -> requeue/skip by policy
```

### 3. Обработка ошибок
```python
# Временная ошибка MAX API
Повторить отправку по лимиту.

# Постоянная ошибка формата/валидности
Прекратить retry и зафиксировать failure.
```
